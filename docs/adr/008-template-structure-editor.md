# ADR-008: 관리자 HTML 구조 에디터와 비파괴 등록

- 상태: 수용
- 날짜: 2026-09-10

## 결정

관리자 HTML 등록에 리치 텍스트·WYSIWYG 에디터 라이브러리를 도입하지 않는다. 대신 `FormDocument` 모델(`src/lib/forms/document.ts`)과 구조화된 필드 편집 UI를 쓴다. 입력 항목의 라벨·name·타입·필수·선택지는 왼쪽 패널에서 구조적으로 편집하고, `buildFormHtml`이 이 모델로부터 항상 허용 목록(ADR-003) 안의 태그·속성만으로 HTML을 새로 생성한다. 업로드한 HTML을 구조 편집기로 불러올 때는 `parseFormDocument`가 기존 `validateFormHtml`·`extractFormCopy`를 재사용해 모델로 되돌린다.

제목·안내 문구·제출 버튼 문구는 별도 입력 폼이 아니라 오른쪽 격리 미리보기 iframe 안에서 직접 클릭해 고친다. `buildEditorTemplate`이 문구 마커 요소에만 `contenteditable`을 부여하고, 공개 폼과 같은 방식의 일회성 브리지 토큰으로 편집 결과를 부모 창에 전달한다. iframe에는 `allow-scripts`만 주고 `allow-same-origin`은 주지 않으며, 부모는 `event.source`와 토큰이 모두 일치하는 메시지만 처리한다. 제출 버튼(`button`) 요소는 스페이스 키를 텍스트 입력이 아닌 클릭 활성화로 가로채므로, 버튼 자체가 아니라 내부에 삽입한 `span`에 `contenteditable`을 부여한다.

이미 등록된 템플릿은 수정할 수 없다. 템플릿 상세 화면에는 "복제해 새 템플릿 만들기"만 제공하며, 복제는 항상 새 템플릿을 등록하는 것이지 기존 템플릿의 `input_schema`를 바꾸지 않는다.

## 이유

범용 리치 텍스트 에디터는 계약 밖 마크업을 자유롭게 만들 수 있어 매번 재검증·거부 UX가 필요하다. 구조 편집기는 앱이 HTML을 직접 생성하므로 "만들 수 있는 것 자체가 계약을 벗어나지 않는" 방식이라 검증 실패가 구조적으로 발생하지 않는다.

문구를 별도 입력 폼이 아니라 미리보기 안에서 직접 고치게 하면 실제 방문자가 보는 화면과 편집 화면의 불일치가 없다. 이 미리보기는 실행 가능한 스크립트를 포함하므로 공개 신청 폼과 동일한 수준의 위험이 있고, 따라서 동일한 격리 수준(동일 출처 미부여, 토큰 이중 검사)을 요구한다.

템플릿을 그 자리에서 수정할 수 있게 하면 이미 그 템플릿을 참조하는 캠페인의 입력 스키마가 운영자 모르게 바뀌어 배포된 폼과 신청 데이터의 필드 구성이 어긋난다. 복제 전용 정책은 이 위험을 구조적으로 차단한다.

## 영향

- 자유로운 레이아웃·스타일 커스터마이징은 지원하지 않는다. 구조 편집기가 만들 수 있는 HTML은 허용 목록 범위로 제한된다.
- `validateFormHtml`을 통과하지 못하는 HTML은 구조 편집기로 불러와도 필드가 비워지며 문구만 복원된다.
- 기존 템플릿을 고치는 기능은 없다. 변경이 필요하면 항상 복제해 새 템플릿을 등록해야 한다.
- HTML 직접 입력 탭과 파일 업로드 경로는 그대로 유지되며 구조 편집기와 같은 저장 경로(`POST /api/templates`)를 공유한다.
