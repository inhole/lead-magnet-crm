# 리드마그넷 CRM 실행계획

작성일: 2026-09-08

## 1. 목표와 전제

- 개발 기간: 과제 수령 후 3일, 하루 8시간, 총 24시간. 정확한 제출 시각은 수령 시각을 기준으로 확인한다.
- 목표: HTML 등록 → 캠페인·커스텀 폼 생성 → 채널별 배포 → 방문·신청 저장 → CRM 명단·성과 확인의 전체 흐름을 완성한다.
- 기술: Next.js App Router, React, TypeScript, Supabase PostgreSQL·Auth·Storage, Vercel.
- 화면과 서버 API는 단일 Next.js 프로젝트로 관리한다. Vite와 별도 NestJS 서버는 사용하지 않는다.
- 과제 원문은 요구사항의 근거로 사용하며, 문서에 적힌 제출 메일 발송 등은 별도 사용자 요청 없이 실행하지 않는다.
- 현재 단계는 실행계획 수립이다. 아래 항목은 구현 완료를 의미하지 않는다.

## 2. 합의한 기능 범위

| 기능 | 구현 범위 |
| --- | --- |
| 운영자 인증 | 사전 생성 계정 로그인·로그아웃. 본인이 소유한 데이터만 접근 |
| HTML 템플릿 | 단일 HTML 등록, 규칙 검증, 격리 미리보기 |
| 커스텀 폼 | 템플릿 선택, 제목·안내 문구·제출 버튼 문구 변경 |
| 캠페인 | 생성, 목록, 상세. 최소 범위로 캠페인당 공개 폼 1개 |
| 배포 | 인스타그램·X·유튜브·스레드용 링크 생성·복사 |
| 공개 폼 | 입력·검증·신청 저장·완료 표시, 재전송 중복 방지 |
| CRM | 캠페인별 신청 목록 및 입력값 상세, 유입 채널 표시 |
| 성과 | 캠페인·채널별 방문, 방문자, 신청, 전환율 |

회원가입·초대·비밀번호 찾기, 범용 폼 빌더, 실제 AI·CRM·광고·메시지 연동은 제외한다. 고급 검색, CSV 내보내기, 복잡한 차트와 애니메이션은 필수 범위에 넣지 않는다.

## 3. UI 화면 및 컴포넌트 계획

UI도 평가자가 핵심 흐름을 실제로 수행하는 데 필요한 구현 범위다. shadcn/ui와 Tailwind CSS를 사용하고 필요한 컴포넌트만 추가한다. 기본 테마와 강조색 하나를 사용하며 공개 HTML 디자인은 격리된 화면 안에서 유지한다.

### 화면

| 화면 | 핵심 구성과 동작 |
| --- | --- |
| 로그인 | 이메일·비밀번호, 제출 중 표시, 로그인 실패 안내 |
| 캠페인 목록 | 캠페인 이름·생성일, 캠페인 생성 버튼, 첫 사용 안내 |
| HTML 등록 | 파일 선택, 작성 규칙·샘플, 검증 결과, 격리 미리보기 |
| 캠페인 생성 | 템플릿 선택, 제목·안내·버튼 문구 입력, 미리보기, 저장 |
| 캠페인 상세 | 성과 요약, 채널 성과 표, 배포 링크, 신청자 목록 |
| 신청자 상세 | 제출 시각·채널·전체 입력값. 대화상자 또는 상세 패널 |
| 공개 폼 | 모바일 우선 폼, 필드 오류, 제출 중 상태, 완료·실패 안내 |
| API 문서 | Swagger UI, 인증 방법, 요청·응답·오류 예시 |

### 공통 컴포넌트

- 관리자 레이아웃: 내비게이션, 페이지 제목, 로그아웃.
- 입력: Button, Input, Textarea, Select, Label, FieldError.
- 정보: Table, Badge, Dialog, Alert, 로딩 표시, 빈 상태, 복사 결과 알림.
- 도메인: HtmlUpload, SandboxedFormPreview, CampaignForm, ChannelLinkList, MetricSummary, ChannelPerformanceTable, SubmissionTable.
- 공개 폼과 관리자 화면은 인증·실행 문맥을 분리한다. 격리 미리보기 컴포넌트를 재사용하더라도 업로드 HTML에 관리자 상태를 넘기지 않는다.

### UI 완료 기준

- 정상 상태뿐 아니라 로딩, 빈 목록, 입력 오류, 서버 오류, 저장 성공 상태가 있다.
- 제출 중 중복 클릭을 막고 실패 시 재시도할 수 있다.
- 입력에는 레이블을 연결하고 키보드로 주요 흐름을 완료할 수 있다.
- 모바일 공개 폼과 데스크톱 관리자 화면에서 가로 넘침 없이 동작한다.
- 성과는 숫자와 표로 먼저 제공한다. 장식용 차트는 필수 기능 완료 이후에만 검토한다.

## 4. HTML 작성 규칙 및 보안

아래 세부 규칙은 일정과 안전한 구현을 위한 기본 가정이며 ADR에 기록한다.

- 하나의 form과 고유한 name을 가진 입력 항목을 요구한다. 라디오 그룹 등 합법적인 동일 name 사용은 타입별 규칙으로 처리한다.
- 제목·안내·제출 버튼의 교체 위치를 명시적인 data 속성으로 표시한다.
- 텍스트, 이메일, 전화번호, 숫자, textarea, select, checkbox, radio를 지원 범위로 정의한다. 파일 첨부는 제외한다.
- 필수 여부·타입 등 입력 스키마를 등록 시 추출하고 서버에서도 검증한다.
- 업로드된 사용자 JavaScript, 이벤트 핸들러, 위험 URL, 임의 form action, 외부 실행 콘텐츠는 허용하지 않는다. 지원 범위를 벗어나면 명확한 오류를 반환한다.
- HTML은 관리자 DOM에 직접 삽입하지 않는다. sandbox iframe과 CSP를 사용하고 동일 출처 권한을 부여하지 않는다.
- 시스템 제출 연결 코드만 허용한다. 부모는 메시지의 source가 해당 iframe인지, 메시지 구조·일회성 식별자가 유효한지 검사한다. opaque origin의 문자열만으로 신뢰하지 않는다.
- 관리자 토큰·쿠키·서비스 키를 iframe에 전달하지 않는다. service role 키는 브라우저에 노출하지 않는다.
- 관리자 API는 세션·소유권을 검사하고 상태 변경 요청의 CSRF 방어를 적용한다. CORS만으로 권한을 보장하지 않는다.
- 업로드 크기, 입력 길이, 공개 요청 제한을 정하고 오류 응답을 문서화한다.
- Storage 파일은 비공개로 관리하고 승인된 경로로만 읽는다.

## 5. 데이터와 성과 정의

| 데이터 | 주요 관계·역할 |
| --- | --- |
| HTML 템플릿 | 운영자 소유권, 저장 경로, 입력 스키마 |
| 캠페인 | 운영자 소유권, 이름, 생성 시각 |
| 캠페인 폼 | 템플릿 연결, 커스텀 문구, 공개 식별자 |
| 배포 링크 | 캠페인 폼과 채널 연결, 추적 식별자 |
| 방문 이벤트 | 폼·배포 링크, 익명 방문자 식별자, 방문 시각 |
| 신청 | 폼·방문 연결, 입력값 JSONB, 중복 방지 키, 제출 시각 |

소유권과 캠페인·방문 관계는 외래 키로 관리한다. 가변 입력값만 JSONB로 저장한다. 입력 필드가 달라지는 문제를 피하도록 초기 범위에서는 등록된 템플릿을 덮어쓰지 않는다.

- 방문: 공개 폼 진입마다 기록하며 새로고침을 포함한다. React 재실행이나 네트워크 재시도가 같은 진입을 중복 기록하지 않도록 이벤트 키를 사용한다.
- 방문자: 캠페인별 익명 브라우저 식별자의 고유 수. 기기·브라우저 변경이나 저장소 초기화는 별도 방문자로 취급한다.
- 신청: 정상 저장 건수. 동일 전송 키의 재시도는 기존 결과를 반환한다.
- 전환율: 신청한 고유 방문자 / 고유 방문자 × 100. 분모가 0이면 0%.
- 채널: 현재 방문에 사용한 배포 링크를 신청까지 연결한다. 채널 없는 직접 방문은 직접 유입으로 분류한다.
- 채널별 고유 방문자 합계는 캠페인의 고유 방문자 수와 다를 수 있다.
- 최초 범위는 전체 기간 집계이며 저장 시각은 UTC, 화면은 한국 시간으로 표시한다.
- 익명 식별자를 저장할 수 없는 환경의 한계와 자동화 트래픽 미제외를 ADR에 기록한다.

## 6. API 및 문서

인증, 템플릿 등록·조회, 캠페인·폼 생성·조회, 배포 링크 생성·조회, 공개 폼 조회·방문 기록·신청 제출, CRM 조회, 성과 조회를 Next.js Route Handlers로 제공한다.

- OpenAPI 명세를 저장소에서 관리하고 /api-docs에 Swagger UI를 제공한다.
- 요청·응답 스키마, 인증, 파일 업로드, 검증 오류, 권한 오류, 중복 재시도 동작을 포함한다.
- 명세와 구현의 상태 코드·필드가 일치하는지 검증한다.
- README에는 실행·테스트 방법만 넣는다. 운영자 계정 준비와 로컬 서비스 준비는 실행 절차에 포함한다.
- HTML 작성 규칙·샘플, 실행계획, ADR은 docs 등 별도 경로로 관리한다.

## 7. 24시간 일정

| 날짜 | 시간 | 작업 및 완료 기준 |
| --- | --- | --- |
| 1일 차 | 2시간 | Next.js·Supabase·Vercel 초기 연결, shadcn·기본 CI, 관리자 레이아웃, 초기 배포 |
| 1일 차 | 3시간 | DB 마이그레이션·접근 정책, 운영자 로그인, 소유권 검사 |
| 1일 차 | 3시간 | HTML 규칙·샘플, 업로드 검증, 격리 렌더링과 제출 연결 검증 |
| 2일 차 | 2시간 | 캠페인 목록·생성, 커스텀 문구·공개 폼 연결 |
| 2일 차 | 3시간 | 채널 링크·방문 기록·신청 검증·저장·중복 방지·완료 화면 |
| 2일 차 | 3시간 | CRM 목록·상세, 성과 집계·표, 로딩·빈 상태·오류 상태 |
| 3일 차 | 3시간 | 전체 E2E·권한·HTML 격리·지표 테스트, 모바일·키보드 점검 및 수정 |
| 3일 차 | 2시간 | OpenAPI·Swagger UI, README·ADR·환경변수 문서 마무리 |
| 3일 차 | 2시간 | 최종 배포, 새 환경 마이그레이션 재현, 배포 환경 성공 흐름 확인 |
| 3일 차 | 1시간 | 예비 시간, 제출물 검수, 제출 메일 초안 |

테스트·명세·ADR은 관련 기능을 구현할 때 함께 작성한다. 마지막 날의 문서 시간은 누락과 일치 여부 점검에 사용한다. 2일 차 종료 시점에 배포 환경에서 신청 후 성과 확인까지 가능해야 한다.

## 8. 자동화 테스트

| 범주 | 필수 사례 |
| --- | --- |
| 전체 성공 흐름 | 로그인 → HTML 등록 → 캠페인 생성 → 채널 링크 방문 → 신청 → 명단·성과 반영 |
| 인증·소유권 | 비로그인 요청 거부, 운영자 A가 B의 조회·수정·파일 접근 불가 |
| HTML 실패 | 규칙 위반·허용되지 않은 요소·과도한 파일 크기 거부 |
| HTML 격리 | 인증 저장소·상위 DOM·관리자 API 접근 및 외부 전송 시도 차단 |
| 신청 실패 | 필수값 누락·타입 위반·위조된 방문 연결 거부 |
| 재시도 | 동일 신청 키 재전송 시 신청 1건 유지, 방문 재시도 중복 방지 |
| 집계 | 새로고침·재방문·복수 채널·직접 유입·0건의 기대 수치 검증 |
| 실행 재현 | 새 DB에 마이그레이션·계정 준비 후 앱 및 테스트 실행 |

권한·DB 제약은 실제 테스트 DB를 사용하는 통합 테스트로 확인한다. 격리와 브라우저 제출 흐름은 브라우저 E2E로 확인한다. 모의 객체 테스트만으로 보안 완료를 판정하지 않는다.

## 15. 애플리케이션 경계와 디렉터리

계획상 디렉터리이며 실제 파일 생성은 구현 단계에서 한다.

```text
src/app/
  (admin)/                 관리자 화면
  login/                   로그인
  f/[publicId]/            공개 신청 화면
  api/                     HTTP Route Handlers
  api-docs/                Swagger UI
src/components/
  ui/                      shadcn 기본 컴포넌트
  campaigns/               캠페인·배포·성과
  forms/                   업로드·격리 렌더링
src/lib/
  auth/                    세션·운영자 권한
  supabase/                서버 클라이언트
  forms/                   HTML 파싱·허용 규칙·스키마
  services/                캠페인·신청·집계 로직
supabase/migrations/       DB·RLS·필수 DB 함수
tests/unit/                로직 검증
tests/integration/         실제 DB·API 검증
tests/e2e/                 브라우저 검증
docs/api/openapi.yaml      API 계약
docs/adr/                  주요 결정
samples/                   정상 및 검증용 HTML
```

- Route Handler는 세션/입력 확인과 HTTP 응답을 담당하고 서비스 함수에서 업무 로직을 처리한다.
- 관리자 데이터 접근은 사용자 세션을 전달한 DB 클라이언트와 RLS를 기본으로 한다. 로그인 성공만으로 운영자 권한을 부여하지 않는다.
- 사전 생성 운영자를 식별하는 테이블 또는 관리 가능한 역할을 두고 일반 인증 사용자와 구분한다.
- 공개 조회·방문·신청은 필요한 필드와 작업만 허용하는 서버 API를 통한다. 공개 사용자가 신청자 목록을 직접 조회할 권한은 부여하지 않는다.
- 서버 특권 키 사용이 필요한 경로는 좁게 한정한다. 해당 경로는 RLS 우회 가능성을 전제로 소유권·입력을 별도로 검증한다.
- 업로드 HTML은 HTML 파서 기반으로 검사한다. 정규식 치환만으로 실행 콘텐츠를 제거하지 않는다.
- 격리된 HTML에는 인증 정보가 포함되지 않은 폼 정의와 제출 결과만 전달한다.
- 프리뷰에서는 실제 방문·신청을 기록하지 않는다.

## 16. API 초안

경로와 응답 필드는 구현 초기 OpenAPI에서 확정하며 화면 호출과 함께 유지한다.

| 메서드·경로 | 대상 | 역할 |
| --- | --- | --- |
| POST /api/auth/login | 비로그인 | 운영자 로그인, 안전한 세션 설정 |
| POST /api/auth/logout | 운영자 | 세션 종료 |
| GET /api/auth/me | 운영자 | 현재 운영자 확인 |
| POST /api/templates | 운영자 | multipart HTML 검증·저장 |
| GET /api/templates | 운영자 | 본인 템플릿 목록 |
| GET /api/templates/{id}/preview | 소유 운영자 | 안전하게 처리한 미리보기 데이터 |
| POST /api/campaigns | 운영자 | 캠페인·폼 생성 |
| GET /api/campaigns | 운영자 | 본인 캠페인 목록 |
| GET /api/campaigns/{id} | 소유 운영자 | 캠페인·폼 상세 |
| PATCH /api/campaigns/{id}/form | 소유 운영자 | 제목·안내·버튼 문구 수정 |
| POST /api/campaigns/{id}/links | 소유 운영자 | 채널별 링크 생성, 기존 링크 재사용 |
| GET /api/campaigns/{id}/links | 소유 운영자 | 배포 링크 조회 |
| GET /api/campaigns/{id}/submissions | 소유 운영자 | 신청 목록, 제한된 페이지 크기 |
| GET /api/campaigns/{id}/submissions/{submissionId} | 소유 운영자 | 신청 상세 |
| GET /api/campaigns/{id}/metrics | 소유 운영자 | 캠페인·채널별 성과 |
| GET /api/public/forms/{publicId} | 공개 | 제출용 폼·스키마, 운영자 정보 제외 |
| POST /api/public/forms/{publicId}/visits | 공개 | 방문 이벤트 기록, 방문 식별자 발급 |
| POST /api/public/forms/{publicId}/submissions | 공개 | 방문 연결 검증·신청 저장 |

- 배포 URL은 /f/{publicId}?ref={linkToken} 형태로 만든다. 채널 문자열을 신뢰하지 않고 DB에 등록된 링크를 조회한다.
- 다른 폼의 linkToken이나 방문 ID를 섞은 요청은 거부한다.
- 방문 기록 후 발급한 추측하기 어려운 식별자와 서버 검증으로 신청을 연결한다. 광고 성과의 완전한 부정 방지를 보장하는 장치로 설명하지 않는다.
- 오류 응답은 code, message, 선택적 fieldErrors, requestId의 일관된 형태로 제공한다. 내부 스택·키를 반환하지 않는다.
- 기본 상태 코드: 생성 201, 조회/수정·멱등 재응답 200, 입력 오류 400, 비인증 401, 운영자 자격 없음 403, 없거나 타인 소유 리소스 404, 멱등 키 충돌 409, 과대 요청 413, 제한 초과 429.
- 동일 멱등 키·동일 요청은 기존 성공 결과를 반환하고, 동일 키·다른 요청은 409로 처리한다.
- 문구 수정은 텍스트로 반영한다. 문구 입력으로 새로운 HTML이나 스크립트를 삽입하지 않는다.

## 17. 데이터 제약과 재현 데이터

- 캠페인·템플릿 소유자를 연결하고, 타인 소유 템플릿을 캠페인에 연결할 수 없도록 검증한다.
- campaign_forms.campaign_id에 유일성을 두어 캠페인당 폼 1개를 보장한다.
- public_id와 link_token은 추측하기 어려운 고유 값으로 생성한다.
- 배포 링크의 (form_id, channel), 방문의 (form_id, event_key), 신청의 (form_id, idempotency_key)에 유일성을 둔다.
- 동시 요청도 중복 저장되지 않도록 DB 제약 또는 트랜잭션을 사용한다. 애플리케이션의 선행 조회만으로 보장하지 않는다.
- 캠페인 생성·폼 연결은 원자적으로 처리한다. 파일 저장과 DB 기록 중 일부가 실패하면 보상 정리 또는 재시도로 복구한다.
- 조회 패턴에 맞춰 소유자·캠페인·폼·방문자 식별자 인덱스를 추가한다.
- 전체 지표와 채널별 지표는 같은 조회 기준을 사용하며 신청 JOIN으로 방문 수가 증가하지 않도록 각각 집계한다.
- 운영자 A/B, 정상 HTML 1개, 빈 캠페인, 복수 채널 방문·신청 fixture를 준비한다. 데모 fixture와 자동화 테스트 데이터는 분리한다.
- 초기 집계 fixture 예: A가 인스타그램 2회 방문 후 1회 신청, B가 X 1회 방문 후 미신청 → 방문 3, 방문자 2, 신청 1, 전환율 50%.
- 추가 사례: 같은 A가 X에서도 방문하면 채널별 고유 방문자 합은 늘지만 캠페인의 고유 방문자는 늘지 않는다.

## 18. 앱 CI 구성과 운영

### 작업 구성

| 작업 | 목적 | 건수 포함 |
| --- | --- | --- |
| quality | lint·typecheck·build | 제외 |
| unit | 입력·집계·HTML 규칙 등 독립 로직 | 포함 |
| integration | 로컬 Supabase 마이그레이션·권한·DB/API | 포함 |
| e2e | Chromium에서 성공 흐름·격리, 모바일 viewport | 포함 |
| harness | Summary 도구 자체 테스트 | 앱 건수와 별도 표시 |

앱 단위·통합 테스트는 Vitest, 브라우저는 Playwright를 계획 기본값으로 둔다. 실제 패키지 버전과 reporter 형식은 설치 시 검증하고 lockfile에 고정한다. 앱 테스트가 생기는 단계에서 각 job을 연결하며 빈 테스트를 성공 처리하지 않는다.

### 결과 보고

- 각 테스트 job은 실제 runner 리포트를 표준 건수 JSON으로 변환하고 scripts/ci/korean_summary.py를 호출한다.
- 각 job의 Summary 제목에 단위·통합·E2E 등 범위를 적는다. 초기에는 job별 Summary로 충분하며 전체 합산을 위해 별도 서비스를 추가하지 않는다.
- 필수 suite가 미실행되거나 결과가 누락되면 완료 기준을 충족하지 않는다. 실패 후에도 리포트 수집을 시도한다.
- 테스트 재시도는 최종 사례 수로 집계하고 flaky 사례가 있으면 별도 표시한다.
- 리포트와 실패 screenshot/trace는 비밀값·신청자 데이터가 없는지 확인하고 7일 보관한다.
- CI 결과 댓글을 자동 게시하기 위해 쓰기 권한을 추가하지 않는다. Actions Summary와 PR Checks를 사용한다.

형식 예시이며 아래 숫자는 앱 테스트의 실제 결과가 아니다.

```text
단위 테스트
총 몇건 : 10
성공 : 8
실패 : 1
오류 : 0
건너뜀 : 1
결과 : 실패
```

### 실패 처리

설치·DB 준비·브라우저 시작 실패는 테스트 성공 0건으로 표시하지 않는다. 실패 단계와 리포트 확인 불가를 표시한다. flaky 원인이 확인되지 않은 반복 재실행으로 제출을 통과시키지 않는다. 통과 기준은 해당 제출 커밋의 필수 앱 job 성공이다.

## 19. 배포·환경변수·제출 순서

### 환경 분리

- 로컬/CI: 로컬 Supabase와 재현 가능한 마이그레이션·테스트 계정.
- 데모: 별도 Supabase 프로젝트와 Vercel 앱. 자동 테스트가 데모 데이터를 초기화하지 않도록 한다.
- Preview 배포는 사용할 Supabase 환경을 명시한다. 데모 DB를 무심코 공유해 테스트 데이터를 섞지 않는다.
- .env.example에는 URL·공개 키·서버 비밀값의 이름과 준비 방법만 두고 실제 비밀값을 기록하지 않는다.
- 계획 변수: NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY, 필요 시 서버 전용 SUPABASE_SERVICE_ROLE_KEY, APP_URL. 설치 SDK와 선택한 서버 인증 방식에 맞춰 최종 확정한다.
- 공개 접두사가 붙은 변수에는 서버 비밀값을 넣지 않는다. 운영자 초기 암호는 저장소·CI 로그에 남기지 않는다.

### 배포 절차

1. 로컬 마이그레이션과 필수 CI를 확인한다.
2. 데모 Supabase 프로젝트에 마이그레이션·Storage 설정을 적용한다.
3. 데모 운영자를 준비하고 Auth URL·허용 경로·앱 URL을 설정한다.
4. Vercel 환경변수·빌드 설정을 반영하고 배포한다.
5. 데모에서 로그인 → HTML 등록 → 캠페인 생성 → 채널 링크 복사 → 시크릿 브라우저 신청 → CRM·성과 확인을 수행한다.
6. 새 환경의 실행·테스트 방법과 Swagger UI를 다시 확인한다.
7. 최종 커밋, CI 링크, 저장소 주소, 데모 주소, 접근 방법, 미완료 항목을 제출 초안에 넣는다.

코드 되돌리기와 DB 마이그레이션은 별도로 취급한다. 실패 시 기존 데이터를 삭제해 맞추지 않고 원인을 수정한다. 제출용 비공개 저장소의 평가자 접근 방법은 실제 제출 전에 확정한다.
