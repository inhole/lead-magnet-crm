# 개발 워크플로

이 저장소는 짧은 단독 과제에 맞춘 GitHub Flow를 사용한다. `main`은 제출 가능한 안정 브랜치로 유지하고 구현은 이슈와 연결된 작업 브랜치에서 진행한다.

## 작업 흐름

1. `docs/execution-plan.md`의 P 식별자와 기존 GitHub 이슈를 확인한다.
2. 중복이 없으면 이슈 템플릿으로 목표·범위·수용 기준·성공/실패 검증을 발행한다.
3. 최신 `main`에서 `type/이슈번호-slug` 브랜치를 만든다.
4. 동작 변경은 테스트와 함께 구현하고 로컬 검증을 실행한다.
5. 영문 type과 백틱으로 감싼 한글 제목 형식으로 커밋하고 push한다.
6. 같은 형식의 PR 제목과 `Closes #이슈번호` 본문으로 `main` 대상 PR을 만든다.
7. 필수 CI가 현재 커밋에서 모두 통과하면 병합한다.

## 브랜치와 PR 계약

| 항목 | 규칙 | 예시 |
| --- | --- | --- |
| 안정 브랜치 | `main` | 직접 기능 개발 금지 |
| 작업 브랜치 | `type/이슈번호-slug` | `feat/12-public-form` |
| type | `feat`, `fix`, `docs`, `test`, `refactor`, `chore`, `ci` | 변경 성격에 맞게 선택 |
| PR 제목 | 커밋 메시지와 동일 | feat + 백틱 한글 제목 |
| 이슈 연결 | PR 종료 문법 | `Closes #12` |

기능, 보안, DB, 공개 API, CI 정책 변경은 반드시 이슈와 작업 브랜치를 사용한다. 추적 가치가 없는 단순 오탈자만 예외로 둘 수 있다.

## 자동 검증

| Workflow / job | 자동 실행 | 책임 |
| --- | --- | --- |
| `PR 운영 정책 / 브랜치·제목·이슈 연결` | PR | 브랜치명, 한글 제목, 동일 번호 종료 이슈 참조 |
| `앱 품질 검사 / lint · typecheck · build` | PR, `main` push | 정적 검사와 production build |
| `앱 품질 검사 / 단위 테스트` | PR, `main` push | Vitest와 한국어 건수 Summary |
| `CI 결과 집계 도구 검증 / 테스트 결과 집계 로직` | PR, `main` push | Summary 도구 자체 검증 |

Supabase 실제 DB 통합 테스트와 Playwright E2E는 P07 범위다. 해당 job이 추가되고 성공하기 전에는 DB 권한·브라우저 격리를 자동 검증했다고 보고하지 않는다.

## 완료 보고

이슈·PR·커밋·현재 SHA의 CI 링크를 근거로 남긴다. 실행 명령, 결과, 미실행 검증, 남은 위험을 구분한다. 설계 결정은 ADR에 기록하고 README에는 실행·테스트 방법만 둔다.
