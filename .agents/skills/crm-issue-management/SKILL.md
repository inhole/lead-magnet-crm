# CRM 이슈 관리

docs/execution-plan.md를 기준으로 3일·24시간 범위에서 작업을 나눈다. 실제 코드와 기존 이슈를 확인해 중복을 피한다. 원격 접근이 불가능하면 로컬 초안을 남기고 게시했다고 말하지 않는다.

## 작업 단위
- 검증 가능한 기능 흐름으로 나눈다. 예: HTML 등록과 격리 미리보기, 채널 방문과 신청 저장.
- 문제/목표, 포함·제외 범위, 수용 기준, 성공·실패 검증, 의존성, 예상 시간을 한국어로 적는다.
- 인증·소유권, HTML 격리, 지표 정의, DB 재현, API 문서를 포함한다.
- 필수와 선택 기능을 구분한다. 작은 과제에 과도한 하위 이슈나 보드를 만들지 않는다.
- 본문은 .github/ISSUE_TEMPLATE/task.md를 사용한다.

## 진행과 완료
- 준비 → 진행 → 검증 → 완료의 의미로 관리한다. 보드가 없으면 체크리스트와 PR 링크로 충분하다.
- PR에는 관련 이슈, 변경 후 동작, 검증 명령·해당 커밋 CI 링크, 미해결 항목을 적는다.
- 실제 구현·필수 테스트·문서가 갖춰져야 완료다. 이전 커밋 CI 성공을 현재 변경의 근거로 쓰지 않는다.
- 실패 시 재현 가능한 후속 작업과 의존성을 남기고 같은 원인에 중복 이슈를 만들지 않는다.

## GitHub 작업
- 저장소는 git remote로 확인한다. 의도한 대상은 inhole/lead-magnet-crm이다.
- 이슈 게시·댓글 요청이 없다면 로컬 초안까지만 작성한다. 게시 요청이 있으면 기존 승인 범위에서 진행한다.
- gh의 긴 본문은 파일과 --body-file을 사용한다.
- 생성 결과가 불확실하면 목록에서 중복을 확인한 뒤 재시도한다.
