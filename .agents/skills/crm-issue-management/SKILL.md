# CRM 이슈 관리

docs/execution-plan.md를 기준으로 실제 코드와 기존 이슈를 확인해 중복을 피한다. 원격 접근이 불가능하면 로컬 초안을 남기고 게시했다고 말하지 않는다.

## 작업 단위

- 검증 가능한 기능 흐름으로 나눈다. 예: HTML 등록과 격리 미리보기, 채널 방문과 신청 저장.
- 문제/목표, 포함·제외 범위, 수용 기준, 성공·실패 검증, 의존성, 예상 시간을 한국어로 적는다.
- 인증·소유권, HTML 격리, 지표 정의, DB 재현, API 문서를 해당 기능에 포함한다.
- 작은 과제에 과도한 하위 이슈나 보드를 만들지 않는다. 본문은 .github/ISSUE_TEMPLATE/task.md를 사용한다.

## 진행과 완료

- 구현 전 동일 목적의 열린 이슈를 검색한다. 없고 이슈 추적이 요청 범위에 포함되면 이슈를 발행해 번호를 확정한다.
- 최신 `main`에서 `type/이슈번호-slug` 브랜치를 만든다. type은 feat, fix, docs, test, refactor, chore, ci 중 고른다.
- slug는 소문자 영문·숫자·하이픈만 사용한다. 예: `feat/12-public-form`.
- PR 제목은 커밋과 같은 형식을 사용하고 본문에는 `Closes #번호`, 변경 결과, 검증 명령·현재 커밋 CI 링크, 미해결 항목을 적는다.
- 실제 구현·필수 테스트·문서가 갖춰져야 완료다. 이전 커밋 CI 성공을 현재 변경의 근거로 쓰지 않는다.
- 실패 시 재현 가능한 후속 작업과 의존성을 남기고 같은 원인에 중복 이슈를 만들지 않는다.

## GitHub 작업

- git remote로 대상 저장소가 inhole/lead-magnet-crm인지 확인한다.
- 이슈 게시·댓글은 사용자 요청 또는 명시된 프로젝트 운영 범위 안에서만 수행한다.
- gh의 긴 본문은 파일과 --body-file을 사용한다. 생성 결과가 불확실하면 목록에서 중복을 확인한다.

## 완료 체크

1. 이슈 번호와 실행계획 P 식별자를 확인한다.
2. 브랜치명이 `type/이슈번호-slug` 계약을 만족하는지 확인한다.
3. 관련 테스트와 문서를 현재 변경에서 검증한다.
4. 커밋·push 후 현재 SHA의 필수 CI를 확인한다.
5. PR이 이슈를 종료 문법으로 연결하는지 확인한다.
